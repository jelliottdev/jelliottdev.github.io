# Complete searches across bounded jobs

This is an implementation contract, not a claim that composite searches are
available to visitors. Existing finite searches and saved results remain valid.

## One question, complete declared scope

The public question retains its aim, ordered method, evaluation rule, input
edition, alphabet and exact pages. A maintained pinned bank defines the complete
set of key settings. Internal ranges divide execution work; they are not new
ideas, experiment pages or user choices.

The parent identity binds that complete declaration and its source pins. Each
job binds the parent identity and its exact range. Changing a source, page,
method, evaluation or key bank creates a different parent. Merely changing
scheduling must not change the scientific question.

## Current foundations

- `pinned-domain-partitions.js` and its Python counterpart plan complete,
  disjoint ranges under the existing program and page-case limits. Planning
  neither admits tasks nor proves that controls fit or pass.
- The maintained bank contains every vector from both historical rotating
  schedules, including the 648 vectors with 324-rune periods. Bank membership
  does not bypass the repeating-key engine's 256-value limit.
- `periodic-key-scope.js` can represent a complete periodic cycle as a finite
  stream for an exact pinned input scope. It retains whole cycles and their
  unused tails, checks the existing finite-stream bound, and binds every input
  page and reset rule. This is a scope-bound representation proof, not global
  equivalence, task admission or an experiment result.

## Required before enabling execution

1. The server derives each child from the immutable parent declaration. It
   must not accept a browser-supplied replacement child list or altered card.
2. Admission binds parent revision, child range, actual compiled domain,
   selected settings, program, official inputs and task identity. Existing
   finite-member checks still validate the bounded executable task.
3. Full independent known-answer controls remain mandatory. A future lazy
   control format must commit to independently generated task and result
   hashes. Expected results cannot be generated by the decoder being tested.
   A control template's presence does not mean every member has passed.
4. Aggregate progress comes from verified unique program-and-page case
   identities. Never add advertised job totals or count duplicate receipts
   twice. If distinct named settings compile to the same computation, retain
   their alias relationship explicitly rather than inventing extra evidence.
5. A negative result requires complete verified coverage and completed evidence
   lookups across the entire parent domain. Finishing a job is not finishing
   the search; finding an opening does not establish a decryption.
6. Pause, resume, retries, service limits, stale source recovery and cancellation
   preserve saved work and the same parent identity. A reload rechecks verified
   evidence before selecting the next missing work.
7. Visitors see one question, one saved-work count and one run/resume action.
   Internal ranges remain invisible. Unsaved local results remain separate
   from saved verified progress.

Enable the composite flow only after these gates pass through the real browser,
server and database loop, including overlaps, source changes and interruption.
