# Factored finite searches

This migration keeps the visitor's complete declared question while removing
repeated page text from its internal representation. It does not add a new
scientific result or a new method category.

## Current integration boundary

The factored compiler, evidence accumulator, runner adapter, paged provider and
offline audit are being validated separately. The public workspace still uses
the existing finite-question path and its original limits. Do not advertise a
large scope as runnable until the HTTP authority, browser workspace, checkpoint
recovery and complete reproduction flow have been tested together.

## Identities and execution

`FiniteSettings.factored` uses the same canonical declaration parser and member
compiler as the existing path. It permits up to 1,024 programs across 75 exact
pages, without changing `FiniteSettings`' legacy 4,096-case default.

`factored-finite-search-compiler.js` binds every stated page, edition, ordered
operation and exact opening. `factored-finite-question.js` stores the common
inputs once and retains program identities and steps. It validates every
program against all pages before branding the domain. Selecting at most twelve
program/page addresses creates ordinary tasks through the maintained engine.
Those tasks retain existing computation-protocol and page-case identities.

The existing runner validates the branded domain, all controls and all selected
tasks before execution. Its worker, cancellation and verified-checkpoint loop
are shared by both domain versions.

## Evidence

The accumulator independently verifies original receipts in bounded chunks.
It retains coverage positions and original receipt references, rather than a
second copy of every transformed page. Compact proofs contain counts and two
SHA-256 bitmap commitments. Bits use sorted program-major, page-major order;
position `i` sets `bytes[i >> 3] |= 1 << (i & 7)`. Unused final bits are zero.

A verified matching output can answer the specified opening question early.
A negative answer requires actual coverage of every declared case. An
unfinished source lookup cannot authorize supposedly new work.

The new provider uses authenticated, question-bound cursor chains, per-table
append high-water marks and an edit/delete fence. Its HTTP caller must compile
the original saved card against the current official source bundle. A cursor
or a caller-supplied domain is not authority to replace that card. Missing
fence or key configuration must return unavailable, never complete.

## Reproduction

The v2 snapshot contains the original card, complete factored domain, compact
coverage commitments and hashes of bounded chunks containing whole original
receipts. The independent Python verifier reconstructs the declaration and
replays supplied receipts. It never executes missing cases. Recorded lookup
status describes the export snapshot; it is not proof that no other public
work exists.

Large exports must preserve all advertised chunks. Multipart downloads extract
into one directory; auditing an incomplete collection must fail explicitly.
Export limits never reduce the original question or change its coverage.
