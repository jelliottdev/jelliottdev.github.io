What a checksum establishes

SHA-256 maps bytes to a 256-bit digest, displayed as 64 hex digits. A matching digest identifies expected bytes under the hash’s security assumptions, not their creator. Changed line endings can change a text file’s hash.

Choose the exact file you mean to check

The original JPEG, its thumbnail, a screenshot of the reader, and an image re-saved by an editor can all show the same page while having different bytes. For image analysis or OutGuess extraction, start with the original file linked by the page record. A screenshot is not a replacement for it.

File you haveCompare against
An original manuscript JPEGThat image’s entry in the catalogue
A downloaded ZIPThe ZIP’s own checksum; after extraction, each member has its own checksum
An extracted signed messageThe signed-block entry, not the enclosing JPEG or message-body entry
A text transcriptionThe same archived, corrected, or reading version—not a different text layer

Renaming a file does not change its content hash. Resaving it, changing text encoding, or converting LF line endings to CRLF can. File size is a useful preliminary check, but equal sizes alone do not establish equal contents.

Verify directly in the browser

  1. Open Downloads and locate “Verify a downloaded file.”
  2. Select the file you actually saved. The verifier computes SHA-256 locally in the browser and compares its hash and byte count against the catalogue.
  3. Read the returned path, not just the word “Verified.” It identifies the catalogue entry whose bytes matched.

The file is not uploaded by this verifier. A “No exact match” result means no matching entry was found in this catalogue. It does not by itself say that the file is malicious or that an alternative archive is false. Check the intended version, whether the download finished, and whether an application modified the file.

Check a download

# PowerShell
Get-FileHash images/lp1-00.jpg -Algorithm SHA256
# Linux
sha256sum images/lp1-00.jpg
# macOS
shasum -a 256 images/lp1-00.jpg

Compare with the catalog or download entry. Hash the actual file, not its displayed preview.

Run from a folder containing images/lp1-00.jpg, or replace the path with your actual download location. The preserved LP1-00 original is 168,876 bytes and its expected SHA-256 is:

184e6f9de8695d99435c2bef4fd7e304a8a0f704dbe04439fa8bf13c4da395a7

Hexadecimal letter case does not change the digest value; PowerShell may display uppercase. Compare all 64 digits. A leading or trailing excerpt of the digest is not the full check.

Check the files inside an extracted bundle

The reference-data bundle includes a Python 3 checker. From the folder where you extracted it, run:

python scripts/verify_bundle.py REFERENCE-DATA-CONTENTS.json

It checks the recorded size and SHA-256 of each listed file, reports missing or changed members, and leaves your files untouched. A mismatch produces a nonzero exit status. Extra files, such as your own experiment outputs, are not part of this check.

If you extract the original-image bundle into the same folder, its separately named manifest remains available too:

python scripts/verify_bundle.py ORIGINAL-IMAGES-CONTENTS.json

Each bundle has its own named manifest; the transcription bundle uses TRANSCRIPTIONS-AND-READINGS-CONTENTS.json. The older name CONTENTS.json is also included for compatibility, but extracting another bundle into the folder can replace that generic copy. Use the separately named files when combining bundles.

The checker confirms agreement with the manifest you supplied. It does not authenticate that manifest, validate the transcription, or check files omitted from the list. Verify the downloaded ZIP against the published catalog separately when you need to establish which bundle you received.

Why invisible text changes matter

The byte sequence 41 0a is A followed by LF. 41 0d 0a is A followed by CRLF. An editor may display them as the same line, but their hashes differ. This small Python 3 example makes the distinction visible:

from hashlib import sha256

lf = b"A\n"
crlf = b"A\r\n"
print(lf.hex(" "), len(lf))
print(crlf.hex(" "), len(crlf))
assert lf != crlf
assert sha256(lf).digest() != sha256(crlf).digest()
# 41 0a 2
# 41 0d 0a 3

Keep the original byte file and any normalized text as separate artifacts. When documenting an experiment, name the version used and record its checksum before applying transformations. See reproducibility.

A hash check and a signature check answer different questions

A catalogue match checks whether your file agrees with the recorded bytes. Its value depends on which catalogue or source you chose to trust: replacing a file and its expected checksum together would still produce a match. A signature check instead verifies the signed content against a public key, whose provenance must also be established. Neither check proves that an interpretation or proposed cipher solution is correct.

The puzzle’s hash target

LP2-56 refers to a page identified by a hash. SHA-512 has 128 hexadecimal digits; it differs from this wiki’s SHA-256 distribution checksums. A hash is not normally reversible into its input. Candidate checks need the correct bytes and serialization.
