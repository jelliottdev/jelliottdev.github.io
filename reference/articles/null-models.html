Comparing patterns with chance: null models and selection

Work through all six arrangements of a small example, then see how choosing a pattern changes the comparison.

A repeat can be real without being unusual. To ask whether it is unusual, specify what other arrangements you are comparing it with. A null model supplies those alternatives and their probabilities. It is a mathematical comparison, not a claim that the manuscript was actually generated at random.

Start with a question the model can answer

Suppose the question is whether neighboring symbols match unusually often, given the symbols already present. Shuffling their order preserves the counts while changing adjacency. Generating fresh symbols uniformly changes both counts and order. These answer different questions.

ComparisonWhat stays fixedWhat can change
Shuffle the entire rune streamLength and each rune’s countOrder, neighboring pairs and row membership
Shuffle within each declared rowEach row’s length and countsOrder within that row
Draw independent uniform runesChosen length and alphabetCounts as well as order

A whole-stream shuffle preserves whole-stream IoC exactly. It cannot tell you whether that IoC is unusually high: every shuffled value ties the original. It can supply a comparison for an order-sensitive measurement such as adjacent matches. See what cipher operations preserve.

An exact example you can inspect completely

Use the synthetic string AABB, with two A symbols and two B symbols. Define the score as the number of neighboring pairs whose symbols are equal. There are three boundaries to inspect. The score for AABB is 2: AA matches, AB does not, and BB matches.

Our model assigns equal probability to each distinct arrangement of these four symbols. There are 4! / (2! × 2!) = 6. Here is the entire comparison set:

ArrangementThree neighboring pairsEqual pairsUnequal pairs
AABBAA · AB · BB21
ABABAB · BA · AB03
ABBAAB · BB · BA12
BAABBA · AA · AB12
BABABA · AB · BA03
BBAABB · BA · AA21

Two of the six arrangements have a score at least as large as the observed 2. The exact upper-tail probability is therefore 2/6 = 1/3. Ties count, and the observed arrangement belongs to the comparison set. This is the probability of a score at least this large under the specified model; it is not the probability that a cipher theory is false or that the text is random.

Why left and right tails are not always complements

Keep the same six arrangements and the observed equal-neighbor score of 2. Four comparison scores are below 2, two tie it, and none is above it. Those three groups exhaust the comparison set:

Comparison with the observed scoreCountFraction
Strictly below: score < 244/6
Tied: score = 222/6
Strictly above: score > 200/6
Inclusive left: score ≤ 261
Inclusive right: score ≥ 221/3

The two inclusive tails overlap at the ties. Therefore 1 − inclusive left gives the strict right tail, not the inclusive right tail. Here that subtraction gives zero, even though two arrangements attain the observed score. Reporting zero as “nothing like this occurs” would discard those two exact ties.

For any finite reference set, let L, E and G count scores below, equal to and above the observation. Then N = L + E + G, the inclusive left fraction is (L + E) / N, and the inclusive right fraction is (G + E) / N. Their sum is 1 + E / N. Declare the direction and tie rule before interpreting the count.

The historical word-length code uses an inclusive left fraction. A question about an excess requires an upper-tail comparison; it cannot be recovered by simply subtracting that left fraction from one when ties occur. Also distinguish a descriptive fraction of corpus files from a calibrated probability under a sampling model. Repeated editions, duplicate files and a first-passage selection affect what population the fraction describes. See the corpus inventory.

The reproduction script below prints the below/tied/above counts and both tail conventions for this exact example. No additional manuscript experiment is implied.

What if you choose the pattern after looking?

Imagine looking for either a large number of equal neighbors or a large number of unequal neighbors, then reporting whichever count is larger. The score is now max(equal, unequal). For AABB it is still 2, but the comparison procedure has changed.

Applying that same choice to every row above gives scores 2, 3, 2, 2, 3, 2. All six are at least 2, so the exact upper-tail probability becomes 6/6 = 1. With three boundaries, one of the two counts must be at least two. The selection rule guarantees the apparent pattern.

This deliberately small example makes every choice visible. A manuscript search may select among many window lengths, offsets, keys or regions. If you report the best score from that search, compare it with the best score produced by the same search on each simulated input. Testing only the winning setting afterward omits the opportunities that helped it win. Record any earlier, informal exploration too; a model of two choices does not account for fifty choices you actually inspected.

Reproduce both calculations

Download the standalone reproduction script, or extract the reference-data bundle and run the commands below from its folder. Only Python 3 is needed; the script reads no manuscript files and makes no network requests.

python scripts/reproduce_null_example.py
python scripts/reproduce_null_example.py --json

The first command prints all six arrangements, their equal and unequal neighbor counts, and the selected score. It reports upper tails of 2/6 = 1/3 and 6/6 = 1. The JSON option exposes the same rows and exact fractions for reuse. Both include ties and the observed arrangement.

Read the calculation

The core calculation is shown below. This enumerates a four-symbol teaching example; do not use factorial enumeration on a manuscript-sized stream.

from fractions import Fraction
from itertools import permutations

orders = sorted({"".join(p) for p in permutations("AABB")})

def equal_neighbors(text):
    return sum(a == b for a, b in zip(text, text[1:]))

def selected_score(text):
    equal = equal_neighbors(text)
    unequal = len(text) - 1 - equal
    return max(equal, unequal)

for text in orders:
    print(text, equal_neighbors(text), selected_score(text))

for score in (equal_neighbors, selected_score):
    observed = score("AABB")
    tail = sum(score(text) >= observed for text in orders)
    print(score.__name__, Fraction(tail, len(orders)))

The final lines are equal_neighbors 1/3 and selected_score 1. The set removes duplicate arrangements caused by repeated symbols. Each distinct arrangement has the same number of labeled permutations here, so assigning them equal weight agrees with uniformly shuffling the four labeled positions.

Applying the reasoning to Liber Primus

  1. Fix the input. Record its hash, rune filtering, headings and boundaries. The n-gram guide shows why removing separators changes adjacency.
  2. Define the score and direction. More repeats, fewer repeats and a maximum across lengths are different statistics.
  3. State the comparison model. Explain what it preserves, what it changes, and why those choices address the proposed question.
  4. Repeat the complete selection. Use identical parameter bounds and scoring rules for the original and comparison inputs.
  5. Keep the outputs. Report ties, comparison counts, software and any random seed. A sampled calculation is not exhaustive enumeration.

A small tail probability can identify a mismatch with a particular model. It does not identify the cause: language, formatting, an inaccurate transcription or another structure may also violate that model. A candidate decryption still needs an explicit transformation and independently checkable output. A large tail probability likewise does not establish randomness or rule out encryption.
