Alphanumeric grids on LP2-49–51

Three plant-bordered sheets, 256 two-character entries, and a reproducible count that preserves case and leading zeroes.

LP2-49–51 contain rectangular arrays of two-character entries made from decimal digits and Latin letters. They are easy to recognize by the tall, curling plant borders on both sides. These arrays are different from the numerical magic squares: an arrangement in rows and columns does not by itself establish an arithmetic rule.

Where the grids appear

The first sheet has three runic rows above its grid, ending in a small red dotted cluster. The middle sheet has no runic rows. The third has four runic rows below the grid. The borders share curling stems, drooping leaves, root-like branches, and groups of filled dots. Compare the originals before treating the ornaments as identical copies.

The surrounding runic pages retain the paired borders: LP2-48 precedes the grids and LP2-52 follows them, each with twelve runic rows. Compare those layouts when deciding the bounds of an analysis.

Together, the archived grids contain (10 + 13 + 9) × 8 = 256 entries. Each entry contains two characters. The count 256 is therefore a count of entries, not runes, bytes, or distinct values. Calling these bytes would require an explicit decoding rule and a check of its outputs.

Repeated entries and distinct tokens

Counting exact two-character strings across all three archived grids gives 161 distinct tokens among the 256 entries. Of these, 92 occur once and 69 occur more than once. “Distinct tokens” counts different spellings; “entries” counts positions, including repetitions.

No token occurs more than four times in this transcription. For a concrete comparison, 0s occurs at LP2-49 row 5, column 5, and at LP2-50 row 5, column 5; row 6, column 4; and row 12, column 4. Grid row numbers exclude the runic text above or below the arrays.

Case must remain part of the comparison: 0X and 0x each occur three times, but they are separate tokens here. Repetition alone does not establish whether an entry represents a letter, a coordinate, a number, or something else. This inventory describes the archived data before choosing such an interpretation.

Reproduce the inventory

The JSON export includes an inventory with frequencies and sequence positions for every distinct token. Regenerating it with the export script recomputes those counts from the page records. This independent short calculation checks the headline counts from the exported entries:

import json
from collections import Counter
from pathlib import Path

data = json.loads(
    Path("exports/alphanumeric-grids.json").read_text(encoding="utf-8")
)
counts = Counter(row["token"] for row in data["records"])
print("entries", sum(counts.values()))
print("distinct", len(counts))
print("singletons", sum(n == 1 for n in counts.values()))
print("repeated tokens", sum(n > 1 for n in counts.values()))
print("maximum frequency", max(counts.values()))

Expected output: entries 256, distinct 161, singletons 92, repeated tokens 69, and maximum frequency 4. Sequence positions in the inventory point back to the coordinate-bearing records; they are not an additional decoding step.

Preserve the spelling of each entry

The first grid row on LP2-49 is 3N 3p 2l 36 1b 3v 26 33. Uppercase and lowercase letters both matter to the record: 0X and 0x, for example, appear as separate entries in its third row. Keep leading zeroes, too. Converting the entries to ordinary integers or uppercasing them would change the data before a hypothesis has been tested.

Some glyphs are easy to confuse, especially zero and uppercase O, or lowercase l and uppercase I. The stored transcription is a source you can reproduce, not a substitute for checking an ambiguous glyph against the original image. A proposed correction should identify its page, row, column, and image evidence. See the transcription guide for the distinction between an image and its text representation.

What an encoding proposal needs to specify

Reading these entries as positional numbers is a testable proposal. It needs an ordered alphabet, a base, an explanation of letter case, and a reading order across rows and pages. Names such as “base 60” or “base 62” alone do not provide that specification. Different symbol orders assign different values to the same entry.

For an alphabet of length b, a two-character entry xy would have value b × index(x) + index(y), using zero-based indices. That equation describes the proposed conversion; it does not show that the manuscript intended it. Keep the surrounding runes and artwork available as context, and distinguish a valid conversion from a demonstrated decipherment.

Reproduce the grid dimensions

Run this Python snippet from the repository root. It reads the archived page records, selects rows consisting entirely of hyphen-separated two-character alphanumeric entries, and checks that every selected row has eight entries. It does not choose a numeral base or change character case.

import json
import re
from pathlib import Path

total = 0
for number in (49, 50, 51):
    page_id = f"lp2-{number}"
    page = json.loads(
        Path(f"data/pages/{page_id}.json").read_text(encoding="utf-8")
    )
    rows = [
        line.removesuffix("/").split("-")
        for line in page["raw"].splitlines()
        if re.fullmatch(r"[0-9A-Za-z]{2}(?:-[0-9A-Za-z]{2})+/?", line)
    ]
    assert rows and all(len(row) == 8 for row in rows)
    count = sum(map(len, rows))
    total += count
    print(page_id, len(rows), 8, count)
print("total", total)

Expected output:

lp2-49 10 8 80
lp2-50 13 8 104
lp2-51 9 8 72
total 256

This check reproduces the dimensions of the stored transcription. It does not independently verify every glyph or prove that a particular traversal is intended. If you alter the transcription format, revisit the row-selection expression rather than assuming an unchanged count means an unchanged grid.

Download entries with coordinates

Use the structured JSON export for scripts or the CSV export for a table. Each entry keeps its page, grid row, column, sequence position, and original two-character token. Rows and columns start at one; the surrounding runic rows are not included in the grid row numbers.

The sequence follows pages 49, 50, and 51, reading each grid left to right and top to bottom. This is a reproducible export order, not a demonstrated cipher traversal. The JSON also records source-file and transcription checksums. Neither export normalizes case or removes leading zeroes.

When importing the CSV into a spreadsheet, set the token column to Text. Automatic number conversion can turn 04 into 4. Use the JSON when you need strings preserved without spreadsheet import settings.

Regenerate either format using the export script:

python scripts/export_alphanumeric_grids.py --format json
python scripts/export_alphanumeric_grids.py --format csv

Both commands print to standard output. The script rejects malformed rows or changed page dimensions rather than silently publishing an incomplete grid. It checks the archived structure; visual verification of ambiguous glyphs remains a separate task.

A reproducible binary representation

A proposed approach converts these entries to binary and arranges the bits as black and white cells. Before testing such an image, specify the digit alphabet, token boundaries, bit width and layout. “Convert base 60 to binary” does not fix all of those choices.

The following audit uses this explicit alphabet, with values 0 through 59 assigned from left to right:

0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwx

Each two-character token is interpreted separately as 60 × first_digit + second_digit. Under this convention, every archived entry is valid and its value is between 0 and 255. There are still 161 distinct values among 256 entries: this interpretation preserves the exact token distinctions. It is a valid representation of the transcription, not proof that this is the intended encoding.

Eight unsigned bits represent values 0–255. The value 256 already needs nine bits. This matters when comparing these tokens with unrelated decimal numbers elsewhere in the manuscript: sharing a rendering method does not mean those numbers fit the same width.

Why base 60 is unique under the byte assumption

Base 60 is more than one base that happens to work here. It is the only possible integer base under three explicit assumptions: each pair is a positional numeral, digit values follow 0–9, A–Z, a–z in that order, and every pair represents one unsigned byte (0–255). The last assumption matters: this argument does not independently prove that the grid contains bytes.

  1. The largest observed digit sets a lower bound. Lowercase x has value 59. A base-b digit must be smaller than b, so b ≥ 60. For example, 0x appears on LP2-49 at grid row 3, column 7.
  2. A large pair sets an upper bound. The entry 4F, at LP2-49 grid row 9, column 2, has value 4b + 15. Requiring it to fit in one byte gives 4b + 15 ≤ 255, hence b ≤ 60.
  3. The bounds meet. Together, 60 ≤ b ≤ 60 leaves exactly base 60. Checking all 256 entries confirms that every digit and resulting value is valid at that base.

Grid rows here exclude the runic text above the array. The coordinate-bearing report lists every x-containing pair and the 4F witness, so the proof can be checked against the original images.

Can the right digit be the more significant one?

Not under these same assumptions. Reversing significance makes 0x worth 59b. Since b must be at least 60, that is at least 3540, already too large for a byte. The observed 2x would be 3542 at base 60. This concerns the two digits inside each pair; it does not decide the order of rows, pages, or bytes in a larger integer.

If the byte bound is removed, bases 61 and 62 become valid representations with larger values. Changing the digit assignment or using a non-positional code also leaves this proof’s scope. Conditional uniqueness is useful because it makes those choices visible; it is not a decipherment or a claim that every other encoding has been eliminated. See search space and bounds.

Preserve every bit and every row

Encode each value in exactly eight bits, with the most significant bit first. Keep the original eight tokens per row, placing each token’s eight bits horizontally. The 32 manuscript rows then produce a 64-column by 32-row bit array. Pages LP2-49, 50 and 51 occupy rows 1–10, 11–23 and 24–32 respectively. A one is black and a zero is white; no row is omitted, no bits are truncated, and no rotations or reflections are applied.

This produces 256 × 8 = 2,048 data bits. Converting each value to its shortest binary spelling instead, with zero represented as “0”, produces only 1,816 bits. Concatenation then loses the eight-bit token boundaries. That shorter representation is divisible by eight too, so checking only whether the total length is a multiple of eight would not catch the changed convention.

Removing spaces and interpreting all 512 characters as one enormous base-60 integer is a third operation. It uses powers of 60 across the entire string instead of treating each two-character token as a separate byte. Likewise, wrapping the resulting bits at a different width, adding padding, reversing bit order or joining other manuscript numbers creates additional variants. Record each change; do not silently replace one representation with another.

Reproduce the conversion

Run python scripts/audit_grid_binary.py --check from the repository or extracted reference-data bundle. The standard-library script reads the coordinate-bearing token export, checks the byte range, preserves row boundaries, and verifies both the JSON report and exact SVG. It makes no network calls.

The report includes each original token, page coordinate, decimal value and eight-bit spelling, plus the source-export hash and resulting byte-stream hash. Save fresh files with python scripts/audit_grid_binary.py --output my-grid.json --svg my-grid.svg; the script refuses to replace existing files. It does not invoke a QR or Data Matrix decoder.

What a barcode experiment would need

The supplied exploration reports attempts at QR-like and Data Matrix-like layouts, but the full plotting script and referenced result images were not included. Its later comments also identify changed bases, inconsistent bit widths and whitespace mistakes. Those reports do not define one fully reproducible negative test, and they do not rule out every barcode proposal.

A clean experiment would freeze the transcription and conversion first, then list the candidate widths, padding rules, page combinations, rotations, reflections and bit polarities. Specify the decoder and version, settings, and what counts as a valid payload. Preserve outputs and errors for every candidate, and use known valid symbols to confirm the decoder works. A visual resemblance alone is not a decoded result.

Keep related variants in one experiment family, with the changed variables and total candidates visible. The rendering above supplies one fixed input representation for that work; it does not claim that a barcode search has been completed. See search space and bounds and documenting a reproducible attempt.

Do the entries beginning with 4 form a special group?

They form a visibly restricted group in the archived transcription: 17 entries begin with 4, and their second characters are drawn from 056789ABDEF. That is 11 distinct suffixes. The other 239 entries begin with 0, 1, 2 or 3 and collectively use 59 distinct suffixes.

Distinct counts do not add across groups: the same suffix can appear after several different first characters. For example, the combined 0–3 set has 59 characters, not 36 + 36 + 41 + 37. Relative to the case-sensitive 62-character set 0–9 A–Z a–z, its missing characters are f, y and z. Relative to the declared base-60 alphabet above, y and z were never allowed, and only f is unobserved.

The byte-range explanation

Under the stated interpretation value = 60 × first + second, an unsigned byte must satisfy 0 ≤ value ≤ 255. A first digit of 4 contributes 240, leaving 0 ≤ second ≤ 15. With this alphabet, values 0–15 are exactly 0–9 A–F. Prefixes 0–3 allow every suffix value 0–59. Thus a smaller suffix alphabet after 4 is already required by this particular byte interpretation.

The observed group omits 1 2 3 4 C from those 16 allowed suffixes. Five missing symbols is different from five distinct observed symbols. Neither the missing set nor the 17 occurrences is forced by the byte bound; both remain observations. To assess surprise, specify a model for the input bytes and account for how the missing set was selected. The range argument does not prove that the manuscript encodes bytes, and it does not rule out a separate role for the 4-prefixed entries.

A published alternative-grid proposal lists 139 entries for prefixes 0–3 and a distinct count of five for prefix 4. The archived recount gives 239 and 11 respectively. This corrects those two summary figures. The directional prime-search reconstruction separately checks its occurrence counts and missing values.

Reproduce the groups

Use the reference-data bundle, preserving its folders, and run this standard-library Python snippet from the extracted root:

import json
from pathlib import Path

rows = json.loads(Path("exports/alphanumeric-grids.json").read_text())["records"]
tokens = [row["token"] for row in rows]
for prefix in "01234":
    suffixes = [token[1] for token in tokens if token[0] == prefix]
    print(prefix, len(suffixes), len(set(suffixes)), "".join(sorted(set(suffixes))))
low = [token[1] for token in tokens if token[0] in "0123"]
high = [token[1] for token in tokens if token[0] == "4"]
assert len(low) == 239 and len(set(low)) == 59
assert len(high) == 17 and len(set(high)) == 11
print("Missing from hexadecimal suffixes:", "".join(c for c in "0123456789ABCDEF" if c not in high))

The final line reports 1234C. For source coordinates and every original token, use the complete grid export. Case and leading zeroes remain significant throughout.
