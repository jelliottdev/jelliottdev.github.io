Repeated rune sequences: bigrams and trigrams

Locate overlapping repeats, reproduce exact counts and rune positions, and distinguish repetition from a cipher claim.

An n-gram is a sequence of n consecutive symbols. A bigram contains two; a trigram contains three. Counting repeated rune n-grams lets you ask which exact sequences recur and where. Unlike a whole-page index of coincidence, this measurement depends on neighboring symbols and their order.

Slide a window, one rune at a time

For the synthetic stream F–U–F–U–F, a three-rune window has three possible starting positions:

	Start, from zero	Window	Included positions

	0	F–U–F	0, 1, 2

	1	U–F–U	1, 2, 3

	2	F–U–F	2, 3, 4


F–U–F is one repeated pattern with two occurrences, starting at 0 and 2. The occurrences share position 2: this procedure counts overlapping windows. Similarly, F–F–F–F contains three overlapping F–F windows, not two. For N runes and a positive window length n, the number of windows is max(0, N − n + 1).

Exactly which stream is counted

The supplied script reads one archived transcription and retains the 29 alphabet runes in source order, including headings. It removes every non-rune: punctuation, spaces, line markers and printed decimal numbers. Windows can therefore cross word, line and paragraph boundaries. They never cross into another page.

This is a rune-stream measurement, not a count of repeated words or preserved visual rows. Removing a separator makes the runes on its two sides adjacent. A study limited to words, rows or body text would need different segmentation and should not be reported as the same test. Unknown characters in the Runic Unicode block cause an error rather than disappearing silently.

Reproduce the report

Use the repository or reference-data bundle; see setup instructions. Python 3 and its standard library are sufficient. The commands read local files and do not use AI or network services.

python scripts/rune_ngrams.py lp2-31 --length 2
python scripts/rune_ngrams.py lp2-31 --length 3
python scripts/rune_ngrams.py lp2-31 --length 2 --output lp2-31-bigrams.json

The output is UTF-8 JSON with the actual runes visible in its strings. Terminal output and the saved report use the same LF line endings. A terminal font without Runic characters may show boxes; inspect the saved UTF-8 file in a suitable editor rather than replacing the symbols. Length defaults to 3 and accepts integers from 1 through 12. An existing output file is never replaced. A page with no archived rune transcription produces an explanatory error.

Each report records the source file’s SHA-256, the complete ordered alphabet and its SHA-256, the filtering rule, rune count, total windows and every pattern occurring at least twice. Each pattern includes its rune indices, Latin labels, count and starting positions. Starts are zero-based rune ordinals after filtering, not Unicode character offsets or image coordinates. Latin labels identify the runes; they are not decoded words. The alphabet array lets you recover each rune from its zero-based index without a separate lookup file. Its hash covers the UTF-8 concatenation of the runes, without separators.

Worked manuscript example: LP2-31

For LP2-31, the archived stream contains 269 runes. Its source SHA-256 is 493cb51478b106dd626ff93625abaf10c9675ad221896b5206809041dfd55b68.

	Window length	Total windows	Distinct patterns occurring at least twice

	2	268	33

	3	267	0


The first three entries in the bigram report each occur three times. The script sorts by descending count, then by alphabet-index tuple, so ties have a reproducible order:

	Rune labels	Indices	Starts

	R–E	4, 18	84, 162, 233

	H–O	8, 3	62, 131, 224

	D–S	23, 15	7, 14, 41


These are selected rows from the full report, not an exhaustive list of repeated pairs. The empty trigram list means every three-rune window is distinct under this rule. A longer exact repeat would contain a repeated trigram, so the same stream also has no exact repeat of length greater than three. This says nothing about approximate matches, other representations, or patterns spanning multiple pages.

Find an occurrence in the original text file

Each pattern’s occurrences list maps the filtered rune positions back to the unchanged transcription. For the R–E pattern in the example above:

	Start rune	Source line / column	Source characters	Exact source slice

	84	4 / 20	[109, 111)	ᚱᛖ

	162	8 / 6	[214, 217)	ᚱ-ᛖ

	233	11 / 11	[310, 312)	ᚱᛖ


The line/column links above open the corresponding transcription row in the page record. For these three occurrences, the source line and displayed text row have been checked to agree. The highlighted row is the whole row, not a marked character range; use the column and exact slice to locate the pair. Open the manuscript reader to compare with the original image.

The second occurrence crosses a hyphen, the archive’s word-separator notation. Filtering makes these runes adjacent, but the preserved source slice keeps the separator visible. All three match the declared rune-stream rule; they would not all qualify under a rule that forbids crossing word boundaries.

source_start and source_end count Unicode characters from zero. The end is excluded: [214, 217) means characters 214, 215 and 216. source_line and source_column count from one. An LF newline starts a new source line; each Unicode character counts as one column, even if a tab or symbol takes a different visual width in an editor. These are neither UTF-8 byte offsets nor pixel positions.

To check the second occurrence directly, run this from the extracted bundle or repository:

from pathlib import Path
source = Path("text/lp2-31.txt").read_bytes().decode("utf-8")
assert source[214:217] == "ᚱ-ᛖ"
print(source.splitlines()[7])  # Source line 8; Python lists start at zero.

The JSON’s source_text field preserves the complete slice, including any intervening separators or newlines. Source-file line numbers can differ from the wiki’s displayed text-row numbers because the reader omits standalone editorial separators. Use the downloaded source file for these coordinates.

What a repeat does and does not establish

Repeated windows are observations about the selected text. Their counts alone do not give a chance probability, a cipher family or a key length. Window overlap also means that the observed windows are not independent samples. A repeated run of identical symbols illustrates the problem: several windows can be produced by one local run.

A fixed reversible alphabet substitution preserves the occurrence positions and counts of corresponding patterns, though it renames their symbols. Arbitrary transposition can change adjacency and therefore these counts. See cipher invariants before using n-grams to rank transformations.

If you compare many window lengths, page subsets or candidate transformations, record the complete search scope and any selection rule. A significance test would need a stated comparison model and must repeat the selection procedure. This guide supplies a descriptive measurement only; it does not publish a new cipher experiment or claim that a technique has solved LP2-31.

Work through a six-arrangement null-model example before assigning a chance probability to a repeat. It demonstrates both a fixed score and a score chosen after inspection.

For equal neighboring runes across LP2-00–55, see doublets and the 4–2–1 pattern. That audit includes all 86 source locations, two boundary conventions and their exact shuffle expectations.

Sources and verification

The separate LP2 trigram-repeat experiment tests an aggregate excess of matching window pairs against 999 page-preserving shuffles. It records 55 observed pairs and an upper-tail p-value of 0.799. Its result page provides a histogram, every observed repeat position, per-page CSV counts and reproduction scripts. This is a specific experiment; the general counting guide above remains applicable to other window lengths without implying those lengths have been tested.

Two repeated-marker claims: locations before interpretation

Two proposed alignments illustrate why a repeated sequence needs exact coordinates and counting rules. This audit searches the archived rune streams of LP2-00–55, retaining headings and removing non-runes. It locates markers only within pages; global positions concatenate the pages in order. All positions below begin at zero.

DJUBEI: 6395, 6389 or 6388?

The six rune labels D J U B E I occur twice under these rules:

	Page	Page rune interval	Global start
	LP2-27	[28, 34)	6555
	LP2-55	[70, 76)	12950

The second occurrence ends the rune stream of LP2-55. The first is followed by AE. An interval written [28, 34) includes positions 28 through 33: its end is excluded.

	Measurement	Calculation	Result
	Start to start	12950 − 6555	6395
	Strictly between the identical six-rune markers	6395 − 6	6389
	Also exclude the AE after the first marker	6395 − 7	6388

6388 = 4 × 1597, but that value uses the additional AE exclusion. AE is not part of the repeated six-rune marker. The identity is reproducible with that boundary; it should not be presented as the unqualified distance between the two copies. Changing the corpus, heading treatment or transcription can change global positions.

O F L OE NG: what the subtraction produces

The five-rune marker O F L OE NG occurs at LP2-30 rune 86 and LP2-52 rune 179. Align those starts and subtract the earlier page from the later page modulo 29. The following sixteen-position span is the one specified in the proposal; the audit does not search lengths or offsets for a better word.

Using zero-based rune indices gives:

F F F F F E A R TH S I G W O TH Y

The matching marker necessarily gives five zeros, represented by F. The next four output runes are E A R TH, which transliterate to EARTH. This is an arithmetic match, not an established word boundary or a validated reading of the surrounding output.

Using prime values, reducing their differences modulo 29 and interpreting each residue as a rune index instead gives:

F F F F F L J X G TH S OE A EO G B

These are different operations. Prime values are not interchangeable with alphabet indices. The comparison below keeps both representations visible; “offset” counts forward from the aligned marker start.

	Offset	LP2-30	LP2-52	Index difference	Prime difference → index label

	0	O	O	F	F

	1	F	F	F	F

	2	L	L	F	F

	3	OE	OE	F	F

	4	NG	NG	F	F

	5	P	TH	E	L

	6	R	EA	A	J

	7	IA	TH	R	X

	8	A	Y	TH	G

	9	O	E	S	TH

	10	T	Y	I	S

	11	O	N	G	OE

	12	EA	G	W	A

	13	G	N	O	EO

	14	AE	IA	TH	G

	15	M	T	Y	B


For example, the first position after the marker compares P (index 13, prime 43) with TH (index 2, prime 5). Index subtraction gives (2 − 13) mod 29 = 18, the index of E. Prime subtraction gives (5 − 43) mod 29 = 20, the index of L. Reversing the subtraction would be another operation again.

Reproduce the locations and arithmetic

Extract the reference-data bundle or use the repository, then run:

python scripts/repeated_marker_audit.py --check
python scripts/repeated_marker_audit.py

The script and full JSON ledger include input hashes, all marker occurrences, source character offsets, both representations and every output in the specified span. This does not reproduce the separate image-only claim that a DJUBEI alignment yields TRUTH: its exact paired intervals and operation have not been established here.

A next test should fix the alignment rule and output range before judging additional text, retain unsuccessful output, and account for the markers and operations already considered. See candidate readings and search space and bounds. Reproducing a short word does not identify a cipher or establish its chance probability.
