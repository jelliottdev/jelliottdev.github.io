2014 sixth onion: four pages in one JPEG stream

Split the archived response into LP1-10 through LP1-13, distinguish the LP1-10 page JPEG from its four-page carrier, and verify the later signed form.

The preserved response from the historical sixth onion service contains the four pages of The Loss of Divinity, LP1-10 through LP1-13. Its HTML body is hexadecimal; decoding it produces 4,240,957 bytes. Four JPEGs follow one another in that stream, without reversal or leftover bytes. A later saved page from the same service contains a signed instruction about submitting the magic squares.

The preceding fifth-onion book-code account reports the sixth onion address. The archived response and exact page-image recovery can be checked independently of those book lookups.

From response body to four pages

The original saved response begins with <!--761-->. The saved HTTP headers also record X-Cicada: 1033; this is an archived header value, not a property inferred from the decoded pages. Hex-decode only the text inside the HTML <body>. Starting at byte zero, take each JPEG through its first ff d9 end marker and continue with the remainder.

LP1-10 has two useful file forms. The archived 4,240,957-byte carrier includes all four JPEGs back to back. Image viewers display its first page and generally ignore the appended bytes. The 754,662-byte page-only JPEG stops at the first end marker. Our earlier page catalogue called the aggregate simply “LP1-10.jpg”; this distinction is now explicit in the reader and downloads. Preserve the carrier when analyzing source bytes or historical packaging. Use the page-only file when you need just LP1-10 as an image.

A later signed submission form

The archive preserves a later HTML form containing a clear-signed instruction. The saved signature verifies under the preserved Cicada key. It asks readers to paste the magic squares into the form, provide a Tor hidden-service URL, host a file-upload script at /cgi-bin/upload, and place their public key at /key.asc. This confirms what the archived instruction said; it does not prove that a particular submission was made or accepted. The three archived square blocks are documented separately.

The next archived stage preserves three further page JPEGs and a signed follow-up. Its first page survives in a smaller source copy, so the two file versions are labelled separately there.

Replay with the preserved files

Download reference-data.zip and original-images.zip, extracting both into the same folder. Run python scripts/replay_2014_sixth_onion.py --check from that folder with GnuPG installed. The script checks source hashes, splits four JPEGs, compares the page-only copies and aggregate carrier, then verifies the later instruction in an isolated keyring. Add --extract-dir recovered-pages to save the four page-only JPEGs without replacing existing files. The report gives each byte count and hash; the manifest pins the captures to the historical repository revision.
